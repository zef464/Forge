# Terraform: полный разбор — что, зачем и как работать

## 1. Что такое Terraform вообще

Terraform — инструмент Infrastructure as Code (IaC): инфраструктура (сервера,
сети, DNS, базы данных...) описывается не кликами в консоли облака, а текстовыми
файлами. Эти файлы лежат в git, ревьюятся как обычный код, и Terraform сам
разбирается, что нужно создать/изменить/удалить, чтобы реальное состояние
облака совпало с тем, что написано в файлах.

Ключевое слово — **декларативность**. Ты не пишешь "создай сервер, потом
подключи к сети, потом открой порт" (это императивный подход, как в bash-скрипте).
Ты пишешь "вот сервер, вот сеть, вот правило файрвола" — а порядок действий и то,
что уже существует и трогать не надо, Terraform вычисляет сам.

Язык, на котором пишутся файлы — **HCL** (HashiCorp Configuration Language),
файлы `*.tf`.

## 2. Из чего состоит конфигурация

Пять типов блоков покрывают 95% того, что ты увидишь:

```hcl
# 1. terraform{} — служебный блок: какие провайдеры нужны, где backend
terraform {
  required_providers {
    yandex = { source = "yandex-cloud/yandex" }
  }
}

# 2. provider{} — настройка конкретного облака (токен, дефолтная зона)
provider "yandex" {
  zone = "ru-central1-a"
}

# 3. resource{} — то, что реально создаётся в облаке
resource "yandex_compute_instance" "app" {
  name = "payments-staging"
  # ...
}

# 4. variable{} / output{} — входы и выходы модуля
variable "size" {
  type    = string
  default = "small"
}

output "server_ip" {
  value = yandex_compute_instance.app.network_interface[0].nat_ip_address
}

# 5. data{} — чтение уже существующего в облаке (не создаёт ничего)
data "yandex_compute_image" "ubuntu" {
  family = "ubuntu-2204-lts"
}
```

Ссылка на атрибут ресурса — всегда `<тип>.<локальное_имя>.<атрибут>`, например
`yandex_vpc_network.this.id`. Это и есть механизм, которым Terraform строит
граф зависимостей: если сервер ссылается на `network.id`, Terraform знает,
что сеть нужно создать раньше сервера — сам, без твоих указаний "сначала это,
потом то".

## 3. Жизненный цикл: init → plan → apply

Это ядро того, "как с этим работать" на практике.

```
terraform init      # скачивает провайдеры, настраивает backend
       │
       ▼
terraform plan       # СУХОЙ ПРОГОН: что изменится, если применить
       │              (ничего не трогает в реальности)
       ▼
terraform apply      # реально создаёт/меняет/удаляет ресурсы
       │
       ▼
terraform destroy    # удаляет всё, что создано этой конфигурацией
```

- **`terraform init`** — выполняется один раз при старте работы с директорией
  и каждый раз, когда меняются провайдеры/модули/backend. Скачивает бинарники
  провайдеров в `.terraform/`, кладёт lock-файл `.terraform.lock.hcl` (его
  **нужно** коммитить в git — он фиксирует хэши версий провайдеров, чтобы
  у всей команды и в CI использовалась ровно одна и та же версия).

- **`terraform plan`** — сравнивает три вещи: (1) что написано в `.tf` файлах,
  (2) что записано в state, (3) что реально есть в облаке (Terraform делает
  refresh — запрашивает актуальное состояние через API). Показывает diff:
  `+` создать, `~` изменить на месте, `-/+` удалить-и-пересоздать, `-` удалить.
  Ничего не меняет — это просто просмотр плана.

- **`terraform apply`** — выполняет план. Интерактивно спрашивает подтверждение
  (`yes`), если не передан флаг `-auto-approve`. Хорошая практика в CI:
  `terraform plan -out=tfplan`, затем `terraform apply tfplan` — применяется
  ровно тот план, что был просмотрен человеком/CI-джобом, без риска, что
  между plan и apply что-то в облаке поменялось.

- **`terraform destroy`** — удаляет вообще всё, что описано в этой конфигурации.
  Используй с большой осторожностью, особенно на shared state.

## 4. State — самая важная и самая опасная часть

`terraform.tfstate` — JSON-файл, в котором Terraform хранит соответствие
"ресурс в моём коде" ↔ "реальный объект в облаке (его ID)". Без state
Terraform не может понять, что уже создано, и будет пытаться создать всё
заново или ничего не найдёт для сравнения.

Пять правил:

1. **Никогда не коммитить state в git.** В нём в открытом виде лежат секреты
   (пароли БД, приватные ключи, токены) — Terraform их туда пишет как есть.
   `*.tfstate*` — обязательно в `.gitignore`.
2. **Никогда не редактировать state руками.** Для точечных правок есть
   команды `terraform state mv/rm/list/show` и `terraform import`.
3. **Использовать remote backend**, а не локальный файл на ноутбуке —
   иначе state существует в одной копии, и если ноутбук сломался, ты потерял
   единственный источник правды о том, что вообще создано.
4. **Backend должен поддерживать locking** — блокировку на время apply.
   Без неё два параллельных `apply` (например, два CI-пайплайна) испортят
   state гонкой.
5. **State шифровать** (encryption at rest на бакете) — в нём секреты.

Пример backend на Yandex Object Storage — в `environments/dev/backend.tf.example`
в этом же архиве.

### Drift

Если кто-то поменял ресурс руками в консоли облака (не через Terraform) —
это называется **drift**. `terraform plan` его покажет как diff между state
и реальностью. Правило: единственный способ менять инфраструктуру — через
`.tf` файлы и `apply`. Ручные правки в консоли ломают модель "код = истина".

## 5. Переменные, values, откуда что берётся

Приоритет (от низшего к высшему, последнее побеждает):

```
1. default в variable{} блоке
2. переменные окружения TF_VAR_<имя>
3. terraform.tfvars (если существует, подхватывается автоматически)
4. *.auto.tfvars (тоже автоматически, в алфавитном порядке файлов)
5. -var-file=... (флаг командной строки)
6. -var "имя=значение" (флаг командной строки)
```

Секреты (токены, пароли) — **не в tfvars-файлах, которые лежат в git**.
Либо `TF_VAR_yc_token` через переменную окружения в CI-секретах, либо
через vault/secret manager.

## 6. Модули

Модуль — это просто директория с `.tf` файлами, у которой снаружи видны
только `variable{}` (входы) и `output{}` (выходы) — всё остальное
инкапсулировано. Вызывается через блок `module`:

```hcl
module "network" {
  source = "../../modules/network/yandex"

  name     = "payments-dev"
  ip_range = "10.0.0.0/16"
}

# использование output другого модуля:
module "server" {
  source     = "../../modules/server/yandex"
  network_id = module.network.network_id
}
```

`source` может быть локальным путём (как у нас), git-репозиторием,
или модулем из registry. В корпоративных/РФ-проектах чаще всего — локальный
путь или собственный git-репозиторий модулей, не публичный registry.

## 7. Workspaces vs директории на environment

У Terraform есть встроенный механизм `terraform workspace new/select` —
несколько state в рамках одной конфигурации. На практике для
dev/staging/prod это плохая идея: слишком легко случайно применить план
к prod, будучи в неправильном workspace, разница между окружениями
видна только в переменных, а не в коде.

Более безопасный и распространённый подход (тот, что уже в проекте) —
**отдельная директория на каждый environment** (`environments/dev`,
`environments/staging`, `environments/prod`), у каждой свой state,
свой backend key, явный `cd environments/prod && terraform apply` —
невозможно перепутать окружение неявно.

## 8. Команды, которые реально используются каждый день

```bash
terraform fmt -recursive       # привести все файлы к единому стилю
terraform validate             # проверить синтаксис и типы (без обращения к облаку)
terraform plan                 # план изменений
terraform apply                # применить
terraform show                 # человекочитаемый вывод текущего state
terraform state list           # список всех ресурсов в state
terraform state show <ресурс>  # детали конкретного ресурса из state
terraform import <ресурс> <id> # завести под управление Terraform то, что
                                # создано руками, без пересоздания
terraform state rm <ресурс>    # убрать из state, не удаляя реальный объект
                                # (например, если ресурс теперь управляется
                                # другим проектом)
terraform output                # посмотреть outputs без полного plan/apply
```

`terraform taint` устарел — вместо него `terraform apply -replace="<ресурс>"`,
если нужно принудительно пересоздать конкретный ресурс (например, VM с
сорвавшимся cloud-init).

## 9. Практический workflow для команды (как это обычно устроено в CI)

```
Разработчик
   │  git push (ветка)
   ▼
CI: terraform fmt -check, validate, plan
   │  план публикуется как комментарий в PR
   ▼
Ревью человеком: смотрят план, а не только код
   │  merge в main
   ▼
CI: terraform apply (план применяется автоматически или по approve)
```

Важно: **plan в CI на PR — обязателен**, apply — либо вручную по кнопке
(для prod), либо auto для dev/staging. Никто не должен запускать
`terraform apply` с ноутбука на shared окружения — иначе локальный
`.terraform.lock.hcl` и версии провайдеров начинают расходиться с тем,
что реально применялось.

## 10. Специфика для России — обязательно к прочтению

### Блокировка реестра

С 2022 года `registry.terraform.io` (и `releases.hashicorp.com`) блокируют
российские IP на уровне HashiCorp. В 2024 то же самое сделал `OpenTofu`
(открытый форк Terraform) для своего registry. Это значит: без настройки
`terraform init` не скачает **ни сам бинарник**, **ни провайдеры** —
ни для Hetzner/AWS, ни для Yandex — с российского IP без обхода.

Решение — **network mirror**. Провайдеры кэшируются на прокси, а Terraform
настраивается ходить туда вместо `registry.terraform.io`. У Yandex Cloud
есть готовое официальное зеркало для этого (`terraform-mirror.yandexcloud.net`),
конфиг лежит в `environments/dev/terraformrc.example` в архиве — положить его
в `~/.terraformrc` (или `%APPDATA%\terraform.rc` на Windows), и `init`
начинает работать без VPN.

Для CI то же самое: положить файл по тому же пути внутри контейнера/раннера,
либо через `TF_CLI_CONFIG_FILE`.

### Лицензия

Terraform с 2023 распространяется по Business Source License (BSL) —
не полностью открытая лицензия, но использование по прямому назначению
(развернуть свою инфраструктуру) не ограничено. Ограничения BSL касаются
тех, кто продаёт конкурирующий Terraform-as-a-service. OpenTofu — форк под
MPL 2.0 (полностью открытая лицензия), команда рассматривала его вместо
Terraform, но у него тоже заблокирован реестр для РФ — та же проблема,
то же решение (зеркало/прокси), выигрыша по доступности нет.

### Облако

Из протестированных на терраформ-поддержку российских провайдеров
Yandex Cloud заметно впереди: провайдер активно поддерживается
(v0.136+ на начало 2026), полное покрытые сети/compute/managed-баз,
официальное зеркало решает проблему init. Selectel тоже имеет рабочий
провайдер. VK Cloud исторически слабее покрыт Terraform'ом — часть вещей
настраивается только руками через консоль/API напрямую.
